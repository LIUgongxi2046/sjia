## 检索与输入依据

读取依据：[数据 LLD](../../sJIA合并MAS预警平台数据LLD.md)、[后端 LLD 第 3 节](../../sJIA合并MAS预警平台后端LLD.md)、[data-design/schema.sql](../../data-design/schema.sql)（64 张基础表）、[data-design/case-schema.sql](../../data-design/case-schema.sql)（18 张病例表）、[backend-design/schema.sql](../../backend-design/schema.sql)（6 张补充表）、[handshake.md 第 7 节](../../backend-design/handshake.md)。

关键采用结论：

- 初始设计的88张业务表包含64张基础表、18张病例表和六张后端补充表。当前全部正式迁移后的126张业务表见QA28，Django框架表分别登记。
- 业务表使用 `sjia` schema；`db_table = 'sjia"."<表名>'`。
- `finite_decimal`、`sha256_hex` 为 PostgreSQL DOMAIN，通过 `core` 应用的 `0001_schema_and_domains` 迁移建立；对应 `FiniteDecimalField`、`Sha256HexField` 自定义字段直接以 DOMAIN 类型建列，禁止固定 scale 的 numeric。
- 医学当地时间 `medical_time.local_datetime` 用无时区 `timestamp`，由 `LocalTimestampField` 表达，时区单独保存。

## 决策与约束

- **复合外键**：Django ORM 不支持复合外键。采用「模型只声明列 + 集中原生 SQL 迁移建复合外键」的方式，全部 `FOREIGN KEY (a, patient_id) REFERENCES t(id, patient_id)` 及 `ALTER TABLE ... ADD CONSTRAINT` 在 `core` 的后续迁移中用 `RunSQL` 建立，与 schema.sql 语义一致。原生 SQL 清单见 `.planning-work/tmp/composite-constraints.sql`。
- **复合主键表**（如`dictionary_alias`、`record_attachment`、`verification_field`、`alert_signal_result`等15张没有id列的表）：现有模型采用代理`id` UUID主键及原复合列UniqueConstraint，唯一性及外键目标语义保持，各models.py维护准确说明。
- **部分唯一索引 / 部分普通索引**：分别用 `UniqueConstraint(condition=...)` 与 `Index(condition=...)` 表达。
- **enum 值域 CHECK**：由 Django `choices` 在应用层校验；关键跨字段 CHECK 与 PostgreSQL 专属函数 CHECK（jsonb_typeof、num_nonnulls、cardinality）在 `core` 后续迁移用原生 SQL 建立，清单见 `.planning-work/tmp/complex-checks.sql`。
- **search_path**：当前基础配置明确使用`public,sjia`，同时读取现有public框架表及全新迁移后位于sjia的框架表。目标实例按实际目录逐项核验表身份和完整字段，业务模型继续使用明确的sjia限定名称。
- **字段类型**：timestamptz→DateTimeField；timestamp→LocalTimestampField；jsonb→JSONField；text[]/uuid[]→ArrayField；bigint 正值→PositiveBigIntegerField；bigint 非负→BigIntegerField(default=0)。
