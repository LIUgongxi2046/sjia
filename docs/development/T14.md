## 当前功能与实现

UI2-04 使用原稿患者入口、照片介绍、步骤提示、同页表单和保存按钮。原药名与资料说明保持原文字；使用状态默认无法确定，日期、月份、准确时间与未知精度分别保存。获准字段允许直接填写日期，实际填写后保存 date 精度；未填写继续保持 unknown，精度与时区在补充信息中选择。采用照片候选时仅登记实际返回的 name 与 source_text，原照片身份和来源原文共同保存；状态与时间恢复未知，需要本人填写。重新识别成功后本页原文需要重新采用；原有文字、出处说明和时间保留，出处确认重新执行。失败保留已有内容并显示实际错误，支持逐页重试。

当前身份、患儿、有效关联、期限、write_record、read_file、manage_draft 与当前字段配置分别限制登记、原件和草稿操作。配置必须属于当前患儿和 therapy；配置中的字段不可写时保持原稿控件并禁止编辑。没有真实配置时不启用正式登记。当前家庭 H5 已使用获准模拟字段配置、模拟关联和本人确认完成保存及读取；撤权前后读取结果与记录保留由独立 `sjia_simulation` 测试验证。草稿保留原药名、状态、独立时间、照片、候选及出处；恢复后重新确认来源。序列化在进入提交状态之前检查完整时间和原件关联，未知医学时间保存 NULL。提交使用原 createRecord 和保存请求流程，服务确认后进入资料查询。

TherapyCandidates 使用 Pydantic 的严格结构；前端在采用实际响应之前通过 AJV 校验 therapy.schema.json。两项候选文字均为非空字符串，不接受附加字段、自动转换或默认补充。移除已采用候选的照片或重新识别该照片时，页面清除依赖该原件的药名和说明，并回到家庭自报来源，要求重新输入。勾选本人确认后，治疗创建请求额外提交 `family_confirmation: true`；状态、时间、药名、分项或照片改变、草稿恢复时会清除勾选。主窗口已在模拟 API 中完成本人确认的审计保存、详情读取及更正要求，并报告十项模拟检查通过；本窗口已完成家庭 H5 保存、刷新读取、草稿恢复、更正历史及原件追溯。

## 本窗口模拟实现与实测记录

`create_record(kind='therapy')` 已在通用记录事务内调用 `create_therapy_events`。原药名及字段来源沿用通用字段、原件附件及 `SourceAnchor` 保存。本人状态仍按 `therapy_status` 原始字段保存；未知值对应的事件动作使用 `regimen_record`，不会借此写入专业药物分类。开始时间与结束时间分别保存在各自 `RecordField`，未知输入保存为 NULL；ongoing 事件只引用开始时间，ended 事件只引用结束时间，未知状态不引用医学时间。当前获准配置内的药物分项分别保存剂量与单位、浓度、途径、频次及间隔值和单位；数据库所需成对字段不完整时事务拒绝提交。分项未知时保持 NULL。

`correct_record` 为治疗记录生成新 `RecordVersion`，并将新事件的 `previous_event_id` 指向旧事件。新子项名称读取更正版本的原药名字段，原版本字段和原事件继续保留。撤销关联的接口检查实测：有效关联读取返回 200；撤销后返回 403；数据库中的模拟原记录仍为 active。

治疗登记页只显示当前配置中可写的分项。恢复旧草稿时缺失的分项使用空值；保存后由服务端根据相同版本字段创建子项。治疗事件读取投影已由主窗口在 `backend/api/therapy_view.py` 实现，并连通共享记录响应、Schema、类型和详情页。页面现按主窗口请求将勾选状态提交为 `family_confirmation: true`；主窗口已完成服务端持久化、审计回读、更正确认及本人确认筛选，并报告十项实际检查通过，证据见 `.planning-work/coordination/root/therapy-confirmation.json`。治疗字段配置曾短暂不可用，主窗口已修复配置用途隔离并更新模拟资格；当前 H5 会话读取治疗字段与原件上传组均返回 HTTP 200。主窗口当前条件证据见 `.planning-work/coordination/root/field-context-http.log` 与 `.planning-work/coordination/root/t33-delivery-current.json`。
