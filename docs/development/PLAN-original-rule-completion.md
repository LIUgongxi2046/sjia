## Atomic work and dependencies

1. **HLH contracts and pure reference engine.** Source-bound original table
   comparisons; molecular alternative; eight criteria including their two
   compound conditions; qualified provenance, interval time, age, fasting,
   specimen and local laboratory reference; explicit unknown/count bounds.
   Clinical thresholds are not copied from the erroneous PRD units. Missing
   software-policy values are mandatory approved inputs, never active defaults.
2. **HLH governed runtime.** Companion input bindings, existing professional fact
   qualification, immutable task snapshots and dependency rechecks, persisted
   result and support read/API. Legacy classification/MS paths stay compatible.
   Optional composition must not make five-of-eight a prerequisite for unrelated
   dynamic warnings. Depends on step 1.
3. **Weighted named dynamic rules.** A separately versioned trigger contract,
   core/general members, positive explicit weights, exact full-denominator
   bounds, explicit core gate and minimum known coverage. No unknown observation
   becomes a normal value. Existing trigger/lifecycle contracts remain usable.
4. **Patient-approved preset choice.** Professionally approved patient-specific
   allowed schedule list and explicit default; guardian chooses an immutable
   allowed version, not numerical parameters. New patient-scoped permission,
   frozen write intent, CAS selection/history and audit. Recheck purpose, source,
   qualifications and selection at listing, saving and queued execution. A choice
   cannot add consent/field permissions or revive revoked configurations.
   Depends on step 3 and the existing controlled configuration lifecycle.
5. **Usable controls.** Support HLH results/provenance and professionally governed
   weighted editing; family approved-preset selection with active version/source,
   uncertainty and revocation states. Reuse current session/scope/async guards.
   New business controls use the separately restored common visual layer.
6. **Integration and regression.** Pure edge matrices, synthetic approved-input
   persistence, revoked/stale/queued selection races, old-rule compatibility,
   actual-component interrupted flows, then one final frozen full backend suite,
   frontend checks/build and allowed local HTTP/browser evidence.

## Clinical and operational boundaries

These algorithms produce reference predicates and explicitly bounded unknowns,
not diagnoses or medical recommendations. Mathematical weight/core/unknown
semantics are engineering contracts that need professional approval before
clinical use. Literature is source evidence, not approval or proof of product
performance. No real patients/providers, clinical approvals or ready-to-use
medical sensitivity presets are fabricated.

The UI demonstration may run the verified frozen backend with the current visual
frontend to avoid changing implementation hashes under its synthetic audit
fixture. Evidence must name that split version; new business endpoints are not
integrated until a later complete snapshot is run. T26 database-content erasure
remains outside this phase because its particular retention decision is pending.

### Patient preset execution contract (2026-10-11)

`patient-alert-presets-1` is an approved, environment/patient/purpose-specific provider configuration. It lists immutable `dynamic-schedule-2` IDs, approved display labels, and a required professional default. It does not copy or invent medical thresholds. Every offered schedule must bind an approved weighted trigger and an active matching family publication release. The family action `select_alert_preset` is separately granted for the existing purpose and whole patient scope; selecting a plan never grants access or changes consent.

Selection uses an intent, payload digest, compare-and-swap selection version, durable immutable choice, same-transaction metadata audit and recoverable receipt. Expiration renews the same intent only after proving no write request exists. A changed assignment or selecting guardian's grant/session epoch makes an existing choice stale and requires explicit reselection. Queued and manually requested current evaluations bind/revalidate the choice; unselected schedules cannot bypass it. Replay remains support-only and cannot publish. Previous choice dependency versions are invalidated on change.

New APIs: GET `/api/patients/{id}/alert-presets`; POST `/api/patients/{id}/alert-preset-selection`; existing intent/query/retry endpoints with `alert_preset_select`. Family route `/alert-presets`. Operational activation still requires real professional approval/validation and applicable existing family publication components.

Published family content also revalidates the captured preset binding on every home/detail eligibility read. An expired/revoked selecting guardian, changed relation, replaced assignment or removed schedule makes the old evaluation stale and its content unavailable even when a different viewer retains permission. Native notification admission/delivery continues to recheck real computation and the same content gate. Dependency edges are supplementary provenance; no claim is made that all authorization changes emit matching graph invalidation events. The live check is required.
