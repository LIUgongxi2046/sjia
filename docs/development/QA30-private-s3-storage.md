## 应用接入设计

完整接入同时覆盖以下条件，各项均保留原始业务验收要求。

1. 存储身份与实际版本分别登记。业务FileObject.object_version继续表达当前业务版本；新增的存储登记关联准确binding、逻辑对象键、实际VersionId、ETag、SHA256、大小及状态。API、Worker和处置任务统一读取该登记，停用后的对象键保留状态，防止重新发布内容。
2. 写入采用现有UploadPart、用途任务和业务幂等身份。外部写入与业务事务之间保留准确状态：业务提交前终止时，后续操作核验已有完整版本及输入；未知提供方响应进入待核验状态，完整版本清单存在歧义时拒绝采用。取消和重试均不得自动删除其他请求可能引用的对象。
3. 原件、用途副本、OCR响应及语音输入统一采用存储适配。既有整件授权、字段范围、处理用途、资料处置、任务预算和专业状态检查继续在读取及调用前执行。范围读取通过实际版本定位，保持现有HTTP206与416语义。
4. 数据迁移同时校验数据库和存储。既有LocalFileStore对象按准确SHA256及大小迁移，保存本地与S3引用对应关系；所有引用核验完成后，由明确配置选择存储。存储缺失、配置变化或版本不符均立即拒绝读取，系统不自动切换存储。
5. 处置证明使用明确的存储类型。现有本地journal中的设备和inode继续只表达文件系统身份；S3使用准确提供方版本、操作身份及实际响应。内容清理、用途处置、证明读取和恢复重放采用同一版本范围。存在共享引用、保留要求或未核清版本时保留对应阻断条件。
6. 恢复以明确目标为单位。备份清单同时固定数据库、原件版本、配置依据和独立处置检查点；恢复对象完成全部SHA256与版本引用重建，准确重放撤销和内容处置后才允许采用。跨Bucket复制与同机重启检查分别记录，完整生产恢复仍需实际目标、独立存储、RTO/RPO及未知外部影响的核验。
7. 运行采用同时核验存储配置和提供方能力。readiness检查准确owner、Bucket、prefix、版本、加密、策略、CA与实际权限；迁移命令和镜像构建不得隐式访问提供方。运行凭据、备份凭据与删除凭据按实际职责限制权限，并提供轮换及失败后的明确运行状态。
8. 部署文件和交接记录共同更新。API、全部Worker、迁移及恢复工具使用同一明确存储配置；S3数据、配置证据和独立处置journal各自具有明确持久性。生产HTTPS、提供方地域、运行负责人、容量与发布条件以准确目标为依据。
